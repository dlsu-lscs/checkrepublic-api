# Prisma and PostgreSQL

## First-time setup

1. Copy `.env.example` to `.env` if you do not already have it.
2. Set `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD` for the local
   Docker service. Set `DATABASE_URL` to the same database and credentials.
   URL-encode special characters in the URL password; keep `POSTGRES_PASSWORD`
   as the actual password. For example, `$` becomes `%24` and `:` becomes `%3A`.
3. Start PostgreSQL, install packages, apply committed migrations, and generate
   the client:

```sh
docker compose up -d db
npm install
npm run prisma:deploy
npm run prisma:generate
npm run dev
```

The host application connects to `localhost:5432`. If the API also runs inside
Docker Compose, use the database service hostname `db` instead. Docker initializes
credentials and the database only when its data volume is empty; editing `.env`
does not change existing PostgreSQL roles or databases.

## Command reference

| Command | Purpose |
| --- | --- |
| `npm run prisma:format` | Format `prisma/schema.prisma`. |
| `npm run prisma:validate` | Validate the schema and configuration. |
| `npm run prisma:generate` | Generate the typed client; does not create database tables. |
| `npm run prisma:migrate -- --name add_example` | Create and apply a migration on a development database. |
| `npm run prisma:migrate -- --name add_example --create-only` | Create a draft SQL migration for review/customization before applying it. |
| `npm run prisma:deploy` | Apply committed pending migrations; use on deployment and fresh checkouts. |
| `npm run prisma:migrate:status` | Check which migrations have been applied. |
| `npm run prisma:studio` | Open Prisma Studio to browse and edit local database records. |
| `npx prisma db pull` | Introspect an existing database into the schema; review the resulting changes. |
| `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` | Check database/schema drift (exit 0: match; 2: differences). |
| `npm test` | Run tests without PostgreSQL. |
| `npm run test:integration` | Run real PostgreSQL tests after applying migrations. |

`npm run dev`, `npm run build`, and the test scripts generate the client
automatically. After changing the schema, always generate again to refresh types.

## Changing the schema

Update `docs/data-model.dbml` and `prisma/schema.prisma` together. Then run:

```sh
npm run prisma:format
npm run prisma:validate
npm run prisma:migrate -- --name describe_your_change --create-only
```

Review the generated `prisma/migrations/<timestamp>_<name>/migration.sql`, then:

```sh
npm run prisma:migrate
npm run prisma:generate
npm run test:integration
npm run build
```

Commit the Prisma schema, migration directories, and `migration_lock.toml`.
Generated client files and `.env` are ignored by Git. Create a new migration for
later changes instead of editing migrations that have already been applied.
For a deployment, build while development dependencies are available, then run
`npm run prisma:deploy` in a job with the Prisma CLI installed before starting the
API. `prisma migrate dev` is intended for development and uses a shadow database.

Use migrations for this project so database history is reproducible. `npx prisma
db push` changes tables without migration history. `npx prisma migrate reset`
drops data and reapplies migrations; use it only for a disposable development
database whose contents you intend to erase.

## Schema and shared service

The initial migration implements the seven tables and six enums in
[`data-model.dbml`](./data-model.dbml). Prisma exposes `User`, `Session`, `Project`,
`Document`, `AuditRun`, `AuditDocument`, and `AuditFinding` with camelCase fields;
`@map` and `@@map` preserve the DBML's snake_case columns, tables, and enum types.
UUIDs are generated by PostgreSQL using `gen_random_uuid()`. `sizeBytes` is a
JavaScript `bigint`; serialize it explicitly (for example, as a string) in API
responses. JSONB defaults are empty arrays, and timestamps include timezone data.
Projects expose `createdAt` and `modifiedAt` as ISO strings in API responses.
Both default to the current time on creation; Prisma updates `modifiedAt` when
the project row changes. Direct SQL updates must set `modified_at` explicitly;
there is no database update trigger. Child document changes do not automatically
update the project row's timestamp.

The schema uses Prisma's `partialIndexes` preview feature to implement the DBML
note: only one QUEUED or PROCESSING run is allowed per project. Terminal runs can
coexist with another active run. See the
[Prisma partial index documentation](https://docs.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes#configuring-partial-indexes-with-where).
All foreign keys restrict deletion; deleting a parent requires handling its
children explicitly according to the retention policy.

The DBML currently omits `projects.revision`, although `data-model.md` describes
it. This implementation follows the DBML and does not add that column. Reconcile
the design documents and add a migration before implementing revision tracking.
DBML notes about file sizes, nonempty names, same-project audit membership,
snapshot consistency, finding outcomes/severity, immutable history, and JSONB
coverage still require application validation; enums and foreign keys alone do
not enforce those workflow rules.

Use the shared service from `src/shared/database` via `app.prisma` inside Fastify
plugins. Inject it into feature services so they share the app's connection pool:

```ts
import type { PrismaService } from '@/shared/database/prisma.service';

export class ProjectService {
  constructor(private readonly prisma: PrismaService) {}

  findOwnedProjects(userId: string) {
    return this.prisma.project.findMany({
      where: { userId },
      include: { documents: true },
    });
  }
}

// Inside a feature plugin: new ProjectService(app.prisma)
```

Import enum values such as `DocumentType` and `AuditStatus` from
`@/shared/database/generated/client`. Import `PrismaService` directly from
`@/shared/database/prisma.service`. The app connects during startup and disconnects on close.
Integration tests require the migrated database and roll back their model
fixtures, leaving application records intact.
